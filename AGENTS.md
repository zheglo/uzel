# AGENTS.md

## 1. Проект и общение

Создаём сайт-портфолио в стилистике SPA.
Работаем последовательно: сначала фронтенд, экран за экраном.

Пользователь начинающий, знания JavaScript и Svelte минимальные.
Объясняй на русском языке, простыми словами и коротко.
Названия API, пакетов и идентификаторов кода сохраняй
в исходном виде.

Один шаг — одна понятная цель.

Не добавляй функции, архитектуру, абстракции и компоненты
на будущее без конкретной необходимости.

Если существенные детали задачи неоднозначны,
уточни их, а не придумывай требования.


## 2. Стек и конфигурация

- Svelte 5, runes mode
- SvelteKit 3.
- TypeScript.
- pnpm — не npm и не yarn.
- UnoCSS с @unocss/svelte-scoped.
- Конфигурация UnoCSS: uno.config.ts в корне проекта.
- better-auth — аутентификация.
- drizzle-orm и drizzle-kit — работа с базой данных.
- Motion (motion.dev) — анимации через vanilla JavaScript API.
  Примеры адаптируй под Svelte 5 и жизненный цикл компонента;
  для DOM-интеграции используй {@attach ...}.
  Подробные правила — в разделе «Анимации» и .cline/skills/motion/SKILL.md.
- Шрифты — преимущественно через Fontsource.
  Выбор семейств может меняться по согласованию с пользователем.
  Текущие подключения проверяй в проекте.


Точные установленные версии проверяй по package.json и lockfile; не считай номера из этого документа источником актуальных patch-версий.

### Актуальность версий и API

- При начале новой задачи по Svelte или SvelteKit оценивай, требуется ли проверить свежие изменения, относящиеся к этой задаче.
- Проверяй их по официальной документации, changelog и руководствам по миграции.
- Не выполняй проверку обновлений после каждого сообщения и не отвлекайся на изменения, не связанные с задачей.

- Если доступное обновление исправляет существенную ошибку, проблему безопасности или даёт полезную для текущей задачи возможность, кратко сообщи об этом и предложи обновление.
- Не предлагай обновляться только потому, что появилась новая версия.
- Не используй новый API, пока не проверишь, что он поддерживается установленной версией.

- Перед предложением обновления укажи:
  текущую и предлагаемую версии, причину обновления, требования к совместимым зависимостям, необходимые изменения и проверки.
- Различай стабильные и предварительные версии.
  Не переходи на prerelease без отдельного согласования.

- Обновление выполняй отдельным согласованным шагом.
  Не совмещай его с реализацией интерфейса автоматически.
- После обновления проверь изменения в package.json и lockfile, выполни согласованные проверки.
- Если нет доступа к актуальным источникам, прямо сообщи об этом и не утверждай, что установлена последняя версия.

## 5. Правила реализации

### Svelte и TypeScript

- Пиши новые и изменяемые компоненты в runes mode.
- Используй $state, $derived, $props и $effect
  по назначению, а не ради самого применения рун.
- Не используй legacy-синтаксис:
  export let, реактивные метки $: и on:click.
- Используй современные обработчики событий:
  onclick и другие соответствующие атрибуты.
- Для вычисляемых значений предпочитай $derived.
  Не используй $effect для обычных вычислений.
- Не используй onMount: это договорённость проекта.
- Для DOM-интеграции анимаций используй {@attach ...}.
- Используй $effect только для реактивных побочных эффектов,
  а не как автоматическую замену onMount.
- Не обращайся к browser-only API при серверном выполнении.
- Используй TypeScript, но держи типы простыми.
- Не создавай сложные дженерики и абстрактные типы без конкретной необходимости.
- Используй типы, предоставляемые SvelteKit, когда они подходят для задачи.

### Общие правила

- Следуй существующей структуре и стилю проекта.
- Перед предложением команды проверь scripts в package.json.
- Не добавляй библиотеку для задачи, решаемой средствами текущего стека.
- Если подходы существенно различаются, коротко объясни разницу и предложи самый простой подходящий вариант.
- Не пиши unit- и e2e-тесты, включая Vitest и Playwright, если пользователь явно этого не попросил.

### Импорты

Для внутренних модулей используй subpath imports через #, настроенные в package.json:

- #lib/foo.ts
- #lib/components/Button.svelte

Для внутренних файлов указывай расширение.
Не заменяй настроенные импорты относительными путями вида ../components/Button.svelte.

Для внешних пакетов используй их публичные пути импорта.
Правило обязательного расширения на них не распространяется.


## 6. Стили и UnoCSS

Используй UnoCSS с @unocss/svelte-scoped.
Не заменяй scoped-интеграцию глобальной.
Не добавляй Tailwind CSS.

Перед работой со стилями проверь uno.config.ts и существующие примеры в компонентах.

### Utilities и конфигурация

- Предпочитай utility-классы для компоновки, размеров, отступов, типографики, адаптивности и состояний.
- Используй только синтаксис, поддерживаемый текущими presets, rules и настройками.
- Не предполагай полную совместимость с Tailwind CSS.
- Не переноси автоматически синтаксис Tailwind CSS 4.
- Не используй @apply: это правило проекта.
- Не добавляй presets, rules и shortcuts без явного согласования.
- Shortcuts допустимы для действительно повторяющихся сочетаний, а не для каждого элемента.
- Не собирай названия utility-классов из частей: например, 'text-[' + color + ']'.
- При условном оформлении выбирай между полностью записанными классами:
  isActive ? 'text-[#ff0000]' : 'text-[#000000]'.
- Если значение стиля должно быть произвольным и меняться во время работы приложения, используй CSS-переменную или inline-стиль, а не динамическую сборку названия класса.
- Для динамических классов проверяй возможности именно текущей scoped-интеграции.
- Не используй сгенерированные хешированные имена классов в исходном коде и селекторах анимаций.

### Цвета

- Не используй токены палитр вроде blue-500.
- Используй явные HEX, RGB, HSL, именованные цвета или существующие CSS-переменные.
- Примеры: text-[#1e293b], bg-[color:var(--surface)].
- Не создавай новые цветовые токены и не меняй палитру без согласования.

### Размеры и типографика

- Для масштабируемых размеров предпочитай vw, vh, clamp(), а при подходящем контейнере — cqw/cqh.
- Используй %, auto, fr и другие значения компоновки, когда они подходят задаче.
– Не используй rem (установлен пресет @unocss/preset-rem-to-px)
- Не используй неявную размерную шкалу UnoCSS: p-4, w-64 и подобные классы.
- Указывай значения явно: p-[2vw], gap-[1vw].
- Фиксированные px используй там, где размер должен быть строго задан; кратко объясняй причину.
- Для адаптивной типографики используй clamp().
- Примеры:
  text-[clamp(16px,2vw,24px)]
  leading-[clamp(20px,3vw,32px)]

### Шрифты

- Текущие семейства:
  - font-sans: Montserrat Variable;
  - font-serif: Playfair Display Variable;
  - font-local: Magical Childhood Regular.
- Montserrat и Playfair Display подключены через Fontsource.
- Magical Childhood Regular подключён локальным файлом.
- Семейства могут быть заменены по согласованию с пользователем.
- При замене согласованно обновляй импорты, настройки
  fontFamily в UnoCSS и явные font-family в CSS.
- Не добавляй дублирующие источники одного семейства.
- Не удаляй старые подключения и файлы, пока не проверишь,
  что они больше не используются.


## 7. Анимации

Используй vanilla JavaScript API Motion (motion.dev).

Перед созданием или изменением Motion-анимаций прочитай .cline/skills/motion/SKILL.md.

Для DOM-интеграции используй {@attach ...}.

Не добавляй Svelte-обёртки, React API, другую библиотеку или новую архитектуру анимаций без согласования.

При переносе примера сохраняй его визуальное поведение. Если поведение неоднозначно, уточни задачу.

Проверяй используемый API по официальной документации с учётом установленной версии.

Не считай stop, cancel и функции отписки взаимозаменяемыми.

Предусматривай очистку анимаций, обработчиков и подписок при завершении соответствующего жизненного цикла.


### Расположение кода анимаций

- Код Motion-анимаций всегда размещай в отдельных
  TypeScript-модулях в src/lib/motion/<название-экрана-или-секции>/.
  Не описывай анимации непосредственно в Svelte-компонентах.
- Примеры:
  - src/lib/motion/hero/
  - src/lib/motion/about/
- Названия папок должны соответствовать принятому в проекте названию экрана или секции.
- В Svelte-компоненте оставляй разметку,
  подключение анимации через {@attach ...}
  и передачу необходимых параметров.
- Не создавай дополнительные уровни папок,
  универсальные обёртки и вспомогательные модули без конкретной необходимости.
- Новые файлы и вынос существующего кода включай в согласуемый объём изменений.
- Импортируй модули через настроенный #lib,
  с указанием расширения:
  #lib/motion/hero/intro.ts.

## 9. Svelte MCP

Используй официальный Svelte MCP для документации Svelte и SvelteKit и проверки подготовленного Svelte-кода.

Документация не отменяет правила проекта и проверку установленных версий.

Вызовы MCP для поиска документации и анализа переданного кода разрешены в рамках текущей задачи без отдельного согласования, если они не изменяют файлы и не запускают команды.

### Документация

В начале нового диалога по Svelte или SvelteKit:

1. Вызови list-sections.
2. Изучи названия и use_cases.
3. Через get-documentation получи разделы, необходимые для текущей задачи.

Не повторяй вызовы после каждого сообщения. Повтори поиск, если тема изменилась, контекст утрачен или нужна новая документация.

Не загружай несвязанные разделы.
Не запрашивай повторно документацию, которая уже доступна и актуальна в текущем контексте.

### svelte-autofixer

При написании или изменении Svelte-кода обязательно используй svelte-autofixer:

- перед отправкой кода как готового решения;
- по возможности перед записью в проект;
- после исправлений, затрагивающих проверенный код.

Разбирай ошибки и рекомендации. Исправляй относящиеся к задаче замечания и повторяй проверку.

Если замечания повторяются, требуют выхода за согласованный объём или не устраняются, остановись и сообщи об этом.

Не исправляй несвязанный код без согласования.

Эта проверка:

- не разрешает редактировать файлы;
- не заменяет pnpm check и pnpm lint;
- не заменяет проверку интерфейса;
- не доказывает корректность всей логики приложения.

### Playground

Вызывай playground-link только после явного подтверждения пользователя.

Предлагать Playground допустимо для отдельного примера вне проекта.

Не создавай Playground-ссылку для кода, уже записанного в файлы проекта.
Не предлагай её после каждого изменения.

### Недоступность инструментов

Если MCP или отдельный инструмент недоступен:

- назови недоступный инструмент;
- не утверждай, что документация или код проверены;
- согласуй дальнейшую работу.


## 10. Проверки и завершение шага

Для изменения кода включай в согласуемый объём:

- pnpm check, если такой script существует;
- pnpm lint, если такой script существует;
- svelte-autofixer, если меняется Svelte-код.

Другие команды, включая build и запуск dev-сервера, также указывай при согласовании, если они нужны.

Не запускай команды без согласования.
Повторно спрашивать разрешение на уже согласованные команды в рамках того же шага не требуется.

Если script отсутствует, инструмент недоступен или проверка обнаружила ошибки, сообщи об этом.

Не добавляй scripts и не исправляй несвязанные ошибки без отдельного согласования.

В итоговом сообщении кратко указывай:

- что реализовано;
- какие файлы изменены;
- какие проверки выполнены и с каким результатом;
- что осталось проверить или согласовать.

Различай:

1. Реализация выполнена.
2. Проверки пройдены.
3. Результат принят пользователем.

При невыполненных обязательных проверках не объявляй результат полностью проверенным.

Шаг считается завершённым после успешных обязательных проверок и подтверждения пользователя.
