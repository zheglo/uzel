# AGENTS.md

## 1. Проект и цель

Мы создаём сайт-портфолио в стилистике SPA.
Делаем последовательно сначала фронтэнд экран за экраном.
Главная цель — по возможности быстро сделать работающий
сайт, сохраняя понятность решений для меня.

## Стек

**Svelte  5.57** (руны) + **SvelteKit 3** — не Svelte 4 и не SvelteKit 2.
**TypeScript**
**pnpm** - не npm и не yarn.
**UnoCSS** (@unocss/svelte-scoped) — вместо Tailwind. Конфиг UnoCSS — `uno.config.ts` в корне проекта.
**better-auth** — аутентификация.
**drizzle-orm** + drizzle-kit — база данных.
**motion** (motion.dev) — анимации, ванильный JavaScript API. Правила интеграции описаны в разделе «Анимации» и skill motion-svelte.

Точные версии, команды и установленные зависимости проверяй по package.json и конфигурации проекта.
Не угадывай их и не обновляй без согласования.

Используй только синтаксис Svelte 5: $state, $derived, $props, $effect. Запрещено использовать export let, onMount, on:click, $: или старую реактивность Svelte 4.

Используй TypeScript, но держи типы простыми. Не создавай сложные дженерики или абстрактные типы без явной необходимости.
Используй преимущества, которые предоставляет SvelteKit в работе с типами.

## Стили и UnoCSS

- Не использовать `@apply` — UnoCSS в Svelte это не поддерживает.
- Не добавлять новые shortcuts, пресеты и правила в `uno.config.ts` без явного обсуждения с пользователем.
- Предпочитай utility‑классы, поддерживаемые текущими пресетами UnoCSS (preset-wind3 и др.) для компоновки, размеров, отступов, типографики, адаптивности и состояний.
- Синтаксис должен соответствовать текущей конфигурации uno.config.ts. Не предполагай поддержку новых классов или синтаксиса, которого нет в активных пресетах.
- Не используй токены палитр вроде blue-500 и аналоги. Используй явные значения: HEX, RGB, HSL, именованные цвета (red, black) или CSS‑переменные: text-[#1e293b], bg-[color:var(--surface)].
- Не предполагай полную совместимость с Tailwind CSS и не переноси автоматически синтаксис Tailwind CSS 4.
- Не создавай новые цветовые токены и не меняй палитру без согласования.
- Новые shortcuts добавляй только для действительно повторяющихся сочетаний и после согласования изменения конфигурации.
- Не создавай shortcut для каждого элемента или компонента.

## Размеры

По умолчанию: vw, vh, clamp(), при возможности — cqw/cqh.
Фиксированные px — только для SVG-анимаций, курсора и других случаев, где размер должен быть строго задан.
Избегай неявных классов, которые опираются на внутреннюю шкалу UnoCSS (вроде p-4, w-64 и т.п.): они скрывают реальные значения и усложняют контроль. Пиши явно: либо относительные единицы (p-[2vw], gap-[1vw]), либо px с обоснованием (w-[24px]).
Типографика на clamp() и относительных единицах: text-[clamp(16px, 2vw, 24px)], leading-[clamp(20px, 3vw, 32px)]

## Импорты и пути

Используй subpath imports через # (настроены в package.json): #lib/foo.ts, #lib/components/Button.svelte. Всегда указывай расширение файла: .ts, .svelte и т.д.
Не используй относительные пути вида ../components/Button.svelte.

## 3. Размер задачи

Один шаг — одна понятная цель.

По возможности работай с одним основным файлом.
Не дроби связанную задачу искусственно:
если для результата нужны несколько файлов,
предложи их изменение одним согласованным шагом.

Перед изменениями:
- перечисли затрагиваемые файлы;
- кратко объясни назначение изменений;
- получи согласие на объём работы.

Не создавай архитектуру, абстракции и компоненты
на будущее без конкретной необходимости.

Не добавляй функции, которых я не просил.
Не выполняй попутный рефакторинг и форматирование несвязанных частей проекта.

Если намерение пользователя нельзя однозначно понять из задачи — спрашивай, а не додумывай.

Перед выполнением изменений включи необходимые проверки
в предлагаемый на согласование объём работы.

Для задач, изменяющих код, обязательны успешные
pnpm check и pnpm lint, если соответствующие скрипты
существуют в package.json.

Если менялся Svelte-код, также обязательна проверка
через svelte-autofixer.

Не запускай проверки без согласования.
Если скрипт отсутствует, проверка недоступна
или обнаружены ошибки, сообщи об этом.
Не добавляй скрипты и не исправляй несвязанные ошибки
без отдельного согласования.

Различай:
- реализация выполнена;
- проверки пройдены;
- результат принят пользователем.

Задача считается завершённой после обязательных проверок
и моего подтверждения.

Разрешено читать обычные файлы проекта,
необходимые для текущей задачи.

Без моего разрешения нельзя:

- запускать команды;
- устанавливать или обновлять зависимости;
- менять конфигурацию и lockfile;
- выполнять Git-операции, изменяющие состояние репозитория;
- отправлять изменения в удалённый репозиторий.

Согласование списка изменений и команд разрешает выполнить их в пределах описанного шага.
Повторное подтверждение каждого отдельного действия внутри этого объёма не требуется.

Изменение зависимостей, конфигурации, lockfile и Git-операции должны быть явно указаны при согласовании.
Общее разрешение реализовать компонент не означает разрешение выполнять эти действия.

Исключение:
разрешено создавать и обновлять HANDOFF.md

цель, выполненное, изменённые файлы, результаты проверок,
нерешённые вопросы и следующий шаг.
Не превращай файл в историю переписки.
Не включай секреты и неподтверждённые результаты.

Это исключение не разрешает запускать команды

Не передавай содержимое .env, приватные ключи, токены и другие секреты.

Не обходи разрешения инструментов.

## 6. Svelte MCP

Используй официальный Svelte MCP для получения документации
Svelte 5 и SvelteKit и проверки подготовленного Svelte-кода.

Документация MCP помогает выбирать API, но не отменяет
ограничения проекта и необходимость проверять установленные
версии по package.json.

### 6.1. Поиск документации: list-sections

В начале каждого нового диалога, когда задача касается
Svelte или SvelteKit, сначала используй list-sections.

Инструмент возвращает доступные разделы документации
с названиями, use_cases и путями.

Изучи названия и особенно use_cases, чтобы выбрать
разделы, относящиеся к текущей задаче.

Не повторяй вызов после каждого сообщения.
Повтори его, если задача перешла к другой теме
и ранее полученного списка недостаточно.

### 6.2. Получение документации: get-documentation

После list-sections используй get-documentation,
чтобы получить все разделы, необходимые для текущей задачи.

При необходимости запрашивай несколько разделов
одним вызовом.

Не ограничивайся описаниями из list-sections:
перед использованием незнакомого API прочитай
соответствующую документацию.

Не загружай разделы, не относящиеся к задаче.
Не запрашивай повторно уже полученную документацию,
если она доступна в текущем контексте и нет причины
проверять её заново.

### 6.3. Проверка кода: svelte-autofixer

При написании нового или изменении существующего
Svelte-кода обязательно используй svelte-autofixer.

Проверяй подготовленный код:
- перед отправкой пользователю как готового решения;
- перед записью в проект, если это возможно;
- после последующих исправлений.

Разбирай все возвращённые ошибки и рекомендации.
Исправляй относящиеся к задаче замечания
и повторяй проверку до их отсутствия.

Не выполняй бесконечные одинаковые вызовы:
если замечание не удаётся устранить, оно повторяется
или требует выхода за согласованный объём,
сообщи об этом пользователю.

Не меняй несвязанный код только ради устранения
замечания инструмента без отдельного согласования.

Если проверка не выполнена или замечания остались,
не представляй код как полностью проверенный.

Проверка через svelte-autofixer:
- не даёт разрешения редактировать файлы проекта;
- не заменяет pnpm check, pnpm lint
  и проверку результата в интерфейсе;
- не подтверждает корректность всей логики приложения.

### 6.4. Playground: playground-link

Используй playground-link только после явного
подтверждения пользователя.

Если подготовлен отдельный пример вне проекта,
можно предложить создать Playground-ссылку.

Не создавай Playground-ссылку для кода,
который был записан в файлы проекта.

Не предлагай Playground после каждого изменения
в проекте.

### 6.5. Недоступность MCP

Если сервер или необходимый инструмент недоступен:
- сообщи, что именно недоступно;
- не утверждай, что документация или код проверены;
- согласуй дальнейшую работу.

Не подменяй фактический вызов инструмента
заявлением о том, что проверка выполнена.
